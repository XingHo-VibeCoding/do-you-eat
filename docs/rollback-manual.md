# 回滚手册 — do you eat

> 用途：线上出事时的应急操作手册。目标：从「决定回滚」到「线上恢复旧版可用」全程 ≤ 10 分钟。
> 首次演练：2026-10-14（Day 26，静态托管路径），实测耗时见文末记录。

## 一、什么情况必须回滚（判断表）

| 症状 | 处置 | 理由 |
|---|---|---|
| 新版页面白屏 / 主 JS 404，用户打不开 | **立即回滚** | 全量用户不可用，一分钟都不能等 |
| 抽卡、收藏、评分核心流程报错走不通 | **立即回滚** | 核心价值受损，热修时间不可预估 |
| 新版把错数据写进库（如评分存错字段） | **先回滚 + 停云函数，再清数据** | 回滚前端不等于回滚数据，脏数据会留底 |
| 只有样式错乱 / 文案错字 / 非核心页问题 | 不回滚，记 issue 热修 | 回滚成本 > 收益，热修更快 |
| 只在某一浏览器出问题 | 不回滚，排查兼容性 | 回滚救不了单浏览器问题 |
| API 网关超时 / 间歇 5xx | 不回滚，先判断是不是云厂商抖动 | Day 26 实测：网关约 1/6 请求挂 20s+，等 10 分钟再定 |
| 分不清是前端还是后端的问题 | 先 curl 探活 API（见第六节） | 探活不通 → 查云函数/网关；探活通 → 查前端，再决定 |

**一句话原则**：全量用户不可用或数据被写脏 → 立即回滚；局部小毛病 → 热修不回滚。

## 二、回滚前 30 秒检查

1. 确认要回滚的**目标版本**：`git tag -l`（如 `v1.0`）或查 `docs/release-checklist.md` 的发布记录表。
2. 确认回滚**范围**：只是前端（静态托管）？还是云函数也要退？判断方法见上表。
3. 工作区有未提交改动时先寄存：`git stash push -u -m "回滚前寄存"`（`-u` 连未跟踪的新文件一起存）。

## 三、静态托管回退（已演练 ✅）

```bash
# 0. 寄存未提交改动（如果工作区不干净）
git stash push -u -m "rollback-wip"

# 1. 切到目标版本（tag 或 commit 号）
git checkout v1.0            # 或 git checkout <commit号>
#    提示 "HEAD is now at ..." 即成功，这是「 detached HEAD 」状态，正常

# 2. 构建
npm run build

# 3. 部署
tcb hosting deploy dist -e doyoueat-d5g36rg7ia785b553

# 4. 验证（见第六节）

# 5. 回到开发状态（演练/热修结束后）
git checkout main
git stash pop                # 取回寄存的改动
```

注意：静态托管回滚**只动前端文件，不碰数据库和云函数**，评分收藏数据都在云上，不受影响。

## 四、云函数回退（备查，未实操）

> 原理：每个云函数的代码就是 `functions/<名>/` 目录，git 历史里每个版本都在。

```bash
# 1. 只把某函数的代码退到指定版本，不动整个工作区
git checkout <commit号或tag> -- functions/<函数名>/

# 2. 重新部署该函数
node.exe <tcb-cli>/bin/tcb fn deploy <函数名> --force -e doyoueat-d5g36rg7ia785b553
```

两个坑（Day 17~24 的经验）：
- `fn deploy` **不复制环境变量**：若曾改过函数的环境变量配置，回滚代码后需到控制台核对 API Key 是否还在。
- 等约 30 秒再验证，函数冷启动需要时间。

## 五、数据恢复（备查，未实操）

| 场景 | 恢复方式 |
|---|---|
| 表结构坏 / 想重置 | 控制台执行 `db/schema.sql` + `db/seed.sql`（可重复执行） |
| 坏版本写入了脏数据 | PostgREST 按条件 DELETE，或控制台 SQL；删完双通道交叉验证（控制台 SELECT + API 各查一次） |
| 误删整个表 | 从 `db/` 契约重建结构，再从备份 JSON 回灌（备份方式见 release-checklist.md 第五节） |

## 六、回滚后验证（必做，缺一不可）

1. **页面可开**：浏览器打开线上地址，能抽卡出食物。
2. **hash 比对**：`curl -s <线上地址>/ | grep -oE 'assets/index-[A-Za-z0-9_-]+\.js'` 与刚部署的 `dist/assets/` 文件名一致（防 CDN 缓存假象）。
3. **API 探活**：`curl -s <API基地址>/health` 返回 200 且 `status: ok`。
4. **核心流程抽查**：抽卡 → 收藏 → 评分 → 刷新评分还在。

**演练结论**：
- 全程（回滚 + 验证 + 恢复）机器时间合计 **17 秒**，含人工验证约 **3 分钟**，远低于 10 分钟目标。
- 瓶颈不在机器在**人**：判断要不要回滚、敲对命令占了大头——所以第一节的判断表才是真正的救命稻草。
- 局限说明：本次旧版（Day 24）与新版（v1.0）的 src 代码相同，构建 hash 相同，页面上看不出变化，验证靠的是 **git 状态（HEAD 位置）而不是肉眼**。真实事故中前后版本 hash 不同，hash 比对就是最硬的证据。
- 取证教训：给人看的「证据截图」要提前备好一键出证工具（本次用 `.workbuddy/tmp/drill-proof.cmd`，双击即出 git 证据）；现场手敲在命令提示符（没有 git）和中文路径粘贴上连踩两个坑。
