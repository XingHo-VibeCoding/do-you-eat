# Day 27｜试用设计说明（项目侧，不发给试用者）

> 配套文件：`docs/day27-outsider-trial.md`（发给试用者那一份）
> 用途：说明每一步在观察什么、哪两处是故意含糊、拿到记录后怎么定优先级、怎么把修复交给 AI、怎么复验。

---

## 一、每一步在观察什么

| 步骤 | 表面动作 | 真正的观察点 |
| --- | --- | --- |
| 第 0 步 | 打开就看 | **价值主张是否自明**。外行一句话能不能说对用途？说成"抽奖""随机菜谱""测试"都算偏差信号。 |
| 第 1 步 | 点「开始干饭」 | 主 CTA 是否**被认出来是按钮**、点击后结果是否立即可懂（菜名 + 描述）。 |
| 第 2 步 | 收藏 → 食物库 → 只看收藏 | **收藏的"回看路径"是否可发现**。这是 Day 14 真人测试已经踩过一次的坑（当时加了「只看收藏」开关），今天验证修复够不够。 |
| 第 3 步 | 填健康档案 → 保存 | **成功反馈是否可信**。页面会出现「已保存」卡片 + 保存时间 + BMI。观察外行凭什么确认"存住了"。 |
| 第 4 步 | 刷新 | **持久化心智**。健康档案实际存在 localStorage（`dye:health:v1`），刷新应该在；但页面写的是「数据只保存在你的浏览器里，不上云」——这句对外行可能读成"刷新就没了"。 |
| 第 5 步 | 改体重再保存 | **保存 vs 清空 的误点风险**。两个按钮并排、样式相近（`btn--primary` / `btn--ghost`），外行可能点错「清空」，一次清光还以为是自己操作失误。 |
| 第 6 步 | 删除 | **删除是否可逆/可确认**。健康档案的「清空」无二次确认，点了就没了。观察外行是否犹豫、是否敢点。 |
| 第 7 步 | 一句话介绍 | 与第 0 步对照：**用过之后理解有没有变准**。变差说明流程本身在制造误解。 |

## 二、两处故意含糊（不要提前解释）

1. **第 4 步**：只说"刷新看看还在不在"，不说去哪看、不说应该显示成什么样。
   → 用来测「成功状态是否自证」。如果用户刷新后说"看不出来"，问题不在用户，在成功反馈太弱。

2. **第 5 步**：只说"改成另一个数字，让它保存下来"，不指出该点哪个按钮。
   → 用来测「保存/清空」这对按钮的**可区分性**。误点「清空」= 真实事故，价值极高。

**判定口径**：如果 ≥2 位试用者在同一处含糊，那是产品问题；只有 1 人卡住，先算个人差异，不急着改。

## 三、主持试用的 5 条纪律

1. 不提示、不解释、不代操作。
2. 对方卡住时**先默数 30 秒**再说话——很多"卡住"会在 30 秒内自己解决。
3. 对方问"这是什么意思"，统一回："你觉得呢？先按你想的试试。"
4. 全程不提"收藏""打卡""数据库""本地存储"这些内部词。
5. 结束后**再补问**开放问题，不要边做边问（会打断真实反应）。

## 四、已知会踩的雷（踩到了先记下，别当场解释）

| 现象 | 现状 | 处置 |
| --- | --- | --- |
| 取消收藏报「收藏失败，点我重试」 | 已知：`DELETE /api/favorites/:foodId` 返回 405（契约 #9 未上线） | 记为**真实用户可见缺陷**，不阻断核心流程，按 P1 处理 |
| 「数据只保存在你的浏览器里，不上云」读不懂 | 文案对开发者准确、对外行含糊 | 若 ≥2 人困惑，按 P1 改成人话 |
| 只在手机上操作、没找到导航 | 四个 tab 在顶部，小屏可能要滚 | 记录设备与屏幕宽度 |

## 五、拿到记录后：怎么选最高优先级

按下面四问给每个卡点打分，**先定级再动手**，不要凭感觉。

| 级别 | 判定条件 | 今天怎么办 |
| --- | --- | --- |
| **P0** | 阻断核心流程（走不完创建→确认→修改→删除），且用户**无法自救** | 立刻修，这是今日"最高优先级修复" |
| **P1** | 造成误解但能绕过；或触发了已知 bug 的可见报错 | 时间允许就今天修；不允许则记入待办 |
| **P2** | 个人偏好、"我觉得可以更好"、加新功能的建议 | **今天不动**（清单明确：不按反馈大改、不加新功能） |

> 排序口径：先看"阻断"，再看"影响人数"，最后看"修复成本"。**两个 P1 不如一个 P0 优先**。

## 七、修复后的复验最小任务（发给同一位试用者，最多 1 分钟）

```
上次的第 [X] 步，我们改了一版。
麻烦你再打开这个链接，只做这一件事：

[复验动作，一句话，只说点什么]

做完告诉我两件事：
1. 这次顺不顺利？（顺利 / 还是卡）
2. 屏幕上你看到了什么？
```

> 复验只验修复点，不重跑全流程；重跑全流程会引入新变量，反而看不清。

## 八、卡住降级：没人可用时自己做（间隔 10 分钟）

找不到第三方时，按清单的降级路径自己走一遍——**间隔 10 分钟**是为了丢掉"我知道答案"的肌肉记忆。

| 项 | 填什么 |
| --- | --- |
| 本次时间 | [开始时刻]（与上一次间隔 ≥10 分钟） |
| 设备 / 屏幕宽度 | [例如：手机 390px / 电脑 1440px] |
| 第一个找不到或不理解的地方 | [第几步 + 屏幕上那句话，原样抄] |
| 我当时想点但没敢点的是 | [按钮名] |
| 我最后是靠什么过去的 | [自己想明白 / 猜的 / 跳过了] |

**降级自测只能证明"有坑"，不能替代真人**——完成标准写的是"一位没参与项目的真人"，真人记录不可省。

## 九、本次修复：第 4 步「刷新」卡点（2026-10-15 已修）

### 根因（两个缺陷叠在一起）

| # | 现象 | 根因 |
| --- | --- | --- |
| 1 | **刷不动** | 脚本让外行"往下拉一下"。手机内容不满一屏时下拉手势不触发刷新；微信内置浏览器会把下拉手势吃掉。外行没有别的刷新手段。 |
| 2 | **刷了也看不出** | 用的是 hash 路由（`#/health`），刷新后仍停在健康档案页、数据也还在，**画面与刷新前像素级一致**。页面没有任何东西能证明"刷新发生过"，也没有东西能证明"数据还活着"。 |

### 修复（方案：刷新按钮 + 时间对照）

| 文件 | 改动 |
| --- | --- |
| `src/pages/HealthPage.tsx` | 卡片内新增「🔄 刷新页面」按钮（点一下 `window.location.reload()`，不依赖浏览器手势，微信内置浏览器也能用）；新增「本次打开页面」时间（组件挂载时生成，刷新必变），与「保存于」（刷新不变）**并排**显示，构成对照证据 |
| `src/lib/constants.ts` | 新增 4 条文案常量：`HEALTH_REFRESH_BUTTON` / `HEALTH_SAVED_AT` / `HEALTH_OPENED_AT` / `HEALTH_REFRESH_HINT`；`formatSavedTime` → `formatDateTime`，**补上秒**（只到分钟的话，一分钟内刷新两行会一模一样，更迷惑） |
| `src/styles/app.css` | 新增 `.health-saved-card__verify` / `.health-saved-card__hint`。刷新按钮放在**卡片底部**，与表单里的「清空」物理隔开，降低第 5 步的误点风险；分隔线方案废弃（`--border` 在白卡上对比太低看不见），改用留白 |

**没动的地方**：副标题「数据只保存在你的浏览器里，不上云」按决策保持不动；收藏取消报 405（契约 #9）未动。

### 复验最小任务（可直接转发给同一位试用者）

```
上次你试的时候，第 4 步刷新那一下不好使，我们改了一版。
麻烦再打开同一个链接，只做这一件事：

1. 点「💪 健康档案」，随便填三个数字，点「保存」
2. 点卡片里那个「🔄 刷新页面」
3. 看看「保存于」和「本次打开页面」这两行

做完告诉我两件事：
1. 这次能刷新吗？（能 / 还是刷不动）
2. 刷新之后，那两行时间，哪一行变了？
```

> 复验只验这一点，不重跑全流程。
> **前提**：线上要能看到新版，必须先部署静态托管（`tcb hosting deploy dist`）。本地预览 = `npm run build && npm run preview` → 打开 `http://localhost:4173/#/health`。

### 怎么判断修好了

- 「保存于」那行**不变** 且 「本次打开页面」那行**变了** → 用户能自己说出"数据还在" → 修好了。
- 用户仍说"刷不动" → 缺陷 1 没解决，继续查具体环境（微信/机型/浏览器）。
- 用户说"两行都变了"或"看不懂这两行" → 缺陷 2 没解决，改文案而不是改功能。
