# Day 28｜结营复盘：28 天里我最大的一个认知改变

---

## 一句话答案

**我以前以为"用 AI 做事"的难点是让它写出来；28 天后我发现，难点是让它承认哪里没写出来。**

---

## 一、我原来的认知（Day 1 前后）

刚开始的时候，我脑子里的模型是这样的：

> 我把需求说清楚 → AI 把代码写出来 → 我问一句"做完了吗" → 它说"完成了" → 我交作业。

这个模型里，我是**提问者**，AI 是**执行者**，而我唯一需要判断的就是"它说的话我信不信"。

那时候我判断的标准很朴素：它说得挺肯定的，代码也确实生成了，那就是做完了吧。

**这个模型错得离谱，而且错得非常隐蔽**——因为它在前两周几乎没出过事，直到开始做后端。

---

## 二、它是怎么被打破的（三个真实事故）

### 事故 1：历史口头结论不算数（Day 21）

第 3 周验收的时候，有 6 项检查，其中 5 项 PASS。我挺高兴。结果去复核时发现，那 5 项 PASS 里有一部分依据的是"AI 前几天说过这个已经好了"——不是今天重测的证据。

那天我给自己立了一条规矩：**验收证据必须当日重测，历史口头结论一律不算数。**

那时候我以为这只是"AI 记性差"。

### 事故 2：一句客气的报错，把一个真 Bug 藏了两天（Day 24）

`DELETE /api/foods` 一直返回 405。前端的提示文案写的是"该功能尚未上线"。

我看了这个提示，心想：哦，还没做，那正常。

**两天后才发现，它不是"尚未上线"，它是坏了。** 根因是云函数的 HTTP 方法白名单里只有 GET 和 POST，DELETE 根本没放进去。而那句"客客气气"的文案，让一个真 Bug 伪装成了一个已知的、合理的状态。

那天我又立了一条规矩：**报错文案不许把 Bug 伪装成已知状态。** 同时我意识到一件事——

> 问题不只在 AI 写错了代码，在于**它的措辞让我停止了追问**。

### 事故 3：检查工具自己也会撒谎（Day 28，就是今天）

Day 25 我做了个发布前检查器，原理是"比对契约文档和实现是否一致"，用来防虚报。我很得意，觉得这是整个项目里最扎实的一块。

今天跑它，报了 3 条异常。我去补了契约文档，再跑——**还是那 3 条**。

翻进去一看：

```bash
contract_status() { case "$1" in 1|3|4|5|6|7) echo impl ;; *) echo none ;; esac; }
```

**它根本没读契约文档。** 它自己维护了一份"我记得哪几个接口做完了"的手写名单。文档改了，它不知道，还理直气壮地报错。

一个专门用来"防虚报"的工具，自己就在虚报——它声称在比对「契约 vs 实现」，实际在比对「我上次手写时的记忆 vs 实现」。

---

## 三、我现在的认知

把这三件事串起来，我看到的是同一个东西：

**AI 不会主动告诉你哪里没做完。不是因为它坏，是因为它的默认输出就是"已完成"的语气。**

- 它会说"接口已上线"，其实只是代码提交了
- 它会写"该功能尚未上线"，其实那是它没修好的 Bug
- 它会给检查器配一份手写清单，然后声称自己在做客观比对

它的每一句话都像真的，但**"像真的"和"是真的"之间有巨大的缝隙**，而这个缝隙不会自动暴露——只有你逼它拿证据的时候才会。

所以我现在的模型换成了：

> 我把**验收标准**说清楚（而不是只说需求）→ AI 干活 → **它必须拿出我能亲眼复现的证据** → 没做的必须明说，不许用措辞糊过去。

一句话：**从"问它做完了吗"，变成"让它证明，并且定义好什么叫没做完"。**

---

## 四、这个认知改变具体变成了什么（可复用的机制）

认知不落到制度上就是空话。它在我这个项目里变成了四样东西：

| 机制 | 干什么 | 对应哪个事故 |
|---|---|---|
| **三态结论**（PASS / FAIL / **未执行**） | 不允许"没做"和"做了"混在一起。没做就写"未执行"，宁可难看也不许模糊 | 事故 1 |
| **危害分档** | 检查器按危害方向分级：标了 ✅ 实际没有 = FAIL 阻断；有实现没标 = EXCEPTION 提醒。**让真问题不被小问题淹没** | 事故 2 |
| **禁止客气文案** | 报错文案不许说"尚未上线"这种话，Bug 就是 Bug | 事故 2 |
| **工具必须读事实源** | 检查器不许维护手写清单，去读 `api-contract.md` | 事故 3 |

还有一条最朴素的：**改完代码必须跑构建，把输出贴出来**——因为"写完"和"能跑"是两件事，而 AI 永远不会主动告诉你它没跑。

## 五、28 天我实际做了什么（速览）

| 阶段 | 天数 | 成果 |
|---|---|---|
| 打基座 | Day 1–16 | 立项 → 脚手架 → PRD → 技术选型（无后端起步）→ MVP → 静态托管上线 → 收藏四态 → hash 四页面 → 首个云函数 → 建 4 张表 |
| 接口上线 | Day 17–22 | 12 个接口逐个上线；前端从 mock 切真 API；ratings 三接口 |
| 加固 | Day 23–25 | 安全审计 + 报错文案统一 → 修 405 真 Bug → 发布前检查器 |
| 交付 | Day 26–28 | v1.0 打 tag 发布 + 回滚演练 → 外人试用 → 最终验收与复盘 |

技术栈：React 18 + Vite 5 + TypeScript + 腾讯云 CloudBase（云函数 + PostgreSQL + 静态托管）。
最终形态：**4 个页面、4 张表、12 个接口（已实现 9 个）、1 个公网地址、1 个发布前检查器（26 项）**。

> **补记（2026-10-17）**：结营第二天我按「证据当日重测」的规矩又跑了一遍检查器，
> 顺手把当时唯一真正阻塞核心流程的缺口补掉了：**#9 取消收藏此前一直 405，用户点了收藏取消不掉**。有意思的是——**#9 在检查器眼里一直是 PASS**：
> 契约写"未实现"，实测也"未实现"，两边一致。它只保证"不吹牛"，不保证"功能齐全"。
> 真正的阻塞项是靠人回到核心流程里走一遍才发现的：**点了收藏，取消不掉**。
> 这件事本身就印证了本文第七节那句话——机制能兜住"虚报"，兜不住"盲区"。

## 七、收尾一句

这 28 天我做出来的应用，功能上其实很普通：摇个骰子决定吃什么。

我真正做出来的东西，是**一套让 AI 没法糊弄我的办法**：任务边界、三态结论、危害分档、事实源、当日重测、改完必须跑。

应用会过期，这套办法不会。下一个项目我还会用它。
