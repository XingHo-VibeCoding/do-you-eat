## 0:00–0:30 ｜用户问题（30 秒）

**一句话**：不是"不知道吃什么"，是"**一个人吃饭的时候，连决定都懒得做**"。

三个具体场景，任选两个讲：

1. **选择过载**：外卖 App 翻 10 分钟，最后点了昨天那家。
2. **记不住**：上次那家黄焖鸡到底好不好吃？收藏夹里有，但没写评价，等于没收藏。
3. **没动力**：一个人开火嫌麻烦，最后靠泡面解决。

**产品怎么回答它**：把"吃什么"从一道问答题，变成一个**动作**——摇一下，出一道菜，吃完打个分，好吃就收藏。决策成本压到一次点击。

> 演示时直接说：这是我 28 天从零做出来的，主题是「一个人也要好好吃饭」。

## 0:30–2:00 ｜核心流程（90 秒，边点边讲）

按顺序点，别跳：

| 时间 | 动作 | 讲什么 |
|---|---|---|
| 0:30 | 打开公网首页 | 地址栏给观众看一眼（这是**真线上**，不是本地跑的） |

## 2:00–2:45 ｜提示词改写（45 秒，这段是加分项）

讲**你学会了怎么跟 AI 下指令**，举 3 个真实发生过的例子（都是这个项目里踩出来的）：

**例 1｜从"帮我修 bug"到"先判断这是不是 bug"**
- 原来的说法：`DELETE /api/foods 一直 405，帮我修一下`
- 改后：`先判断这是真 Bug 还是已知状态；如果是 Bug，连根因一起查，不许用"该功能尚未上线"这类文案把 Bug 伪装成已知状态`
- 结果：查出来根因是云函数方法白名单只有 GET/POST，而前端把 405 特判成了"尚未上线"——**一句客气的报错，把一个真 Bug 藏了两天**

**例 2｜从"帮我写个检查清单"到"检查必须读事实源"**
- 原来的说法：`写个发布前检查脚本`
- 改后：`验证工具不许自己维护一份手写清单，要去读契约文档；标了 ✅ 实际没有 = 阻断，有实现没标 ✅ = 提醒`
- 结果：Day 28 就抓到检查器自己在硬编码"我觉得哪几个接口实现了"，把它改成解析 `api-contract.md`

**例 3｜从"给我命令"到"给我的命令必须带重试"**
- 背景：API 网关实测约 1/6 请求会挂 20 秒以上
- 改后：所有探测命令自带一次重试；并且区分"失败位置漂移 = 网络抖动"和"固定位置失败 = 真 Bug"
- 结果：不再把网络抖动误判成接口挂了

**收尾一句**：AI 不怕你要求细，怕的是你把"大概齐"当成需求。

## 2:45–3:20 ｜验证方式（35 秒）

不要说"我测过了"，说**你怎么让人当场复验**：

1. **一条命令跑 26 项**：`bash scripts/verify.sh` → 今天结果 PASS 26 / FAIL 0 / EXCEPTION 1，退出码 0
2. **四条底线手工验**（验收表第三节有完整命令）：健康接口 200 → 食物列表 9 条 → 写入评分 200 → 隔 3 秒取回仍在 → 删除 204
3. **双通道交叉验证**：同一条数据在 ratings 和 favorites 两条链路上各验一次，避免"单个接口偶然成功"
4. **代码一致性**：本地构建产物 `index-DqbCk9z7.js` 与线上主 JS 同名同字节，证明线上跑的就是仓库这份代码

**诚实一句**：10 项里 9 项 PASS，**1 项部分通过**——评分还存本地没上云（后端接口已上线并实测通过，前端没接线）。这个我写在验收表里，没有藏。

## 3:20–3:55 ｜平台限制（35 秒，讲 4 条就够）

挑最有信息量的四条，说明**你不是没做，是平台不给**：

1. **数据库不能直连**：体验版共享集群不提供 PostgreSQL 地址，`pg` 库 TCP 连不上 → 只能走官方 PostgREST REST API + API Key（Day 17 定稿）
2. **路由前缀会吃掉子路径**：云函数绑到 `/api/health` 后，`/api/health/profile` 被它吞掉（契约 #10），健康档案接口至今实现不了
3. **CLI 能力残缺**：`fn deploy` 不复制环境变量（新函数要单独配 API Key，配完还得等 30 秒）；默认域名上禁止用 CLI 建路由，只能去控制台点
4. **体验版会到期**：2027-03-26 到期，不支持自动续费、不支持买资源包；PostgreSQL 按 CU 核秒 + 容量持续计费，**没人访问也在扣**（当前已用 220.96 / 3000 点）

**收尾一句**：这些限制我全都登记在契约和验收表里，标"未实现"而不是标"已完成"。

## 3:55–4:40 ｜后续优化计划（45 秒）

课程到结营为止，下面三项是**结营后自己迭代**的方向，不是欠账。按野心从大到小说：

1. **接一个真实数据源**（教材附录 F 方向）——现在 54 道菜是我手写进 `src/data/foods.ts` 的，数据量靠人工堆。
   换成真实数据源（公开菜谱 API / 结构化表格导入），`db/seed.sql` 改成从源生成，菜品就能持续长。
   契约不用改：`Food` 的类型和 4 张表结构已经定好，换的是"数据从哪来"，不是"数据长什么样"
2. **加注册登录**（教材附录 D 方向）——现在是匿名方案：前端生成 UUID 存 localStorage，每次请求带 `X-User-Id` 头，
   服务端**不建 users 表**。好处是接口形状与身份来源解耦：将来升级正式登录，
   `X-User-Id` 换成 token 解析出的 userId，**12 个接口一行都不用改**
3. **给核心记录加统计页**——**不用加后端接口**：现有 `GET /api/ratings` 和 `GET /api/favorites`
   已经能拿到全部评分与收藏，前端拉下来画图表即可（打分分布 / 最常吃的餐段 / 收藏 Top N）。
   这是"复用现有 GET 接口 + 前端图表"，成本最低、见效最快
4. 带过：评分上云（`storage.ts` 换 API，后端早就好了）、#10/#11/#12 健康档案（#10 要绕开前缀路由，比如改绑 `/api/profile`）

**最后一句**：28 天最大的收获不是这个应用，是**学会了怎么让 AI 别糊弄我**——包括让 AI 承认自己哪里没做完。
