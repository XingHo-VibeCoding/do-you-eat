## 第一段：用户问题（约 30 秒）

- **表面问题**：「今天吃什么」是每天的选择困难——第 2 周的前端已经用抽卡解决了它。
- **第 3 周真正要回答的问题**：数据住在哪？第 2 周所有数据（收藏、评分、健康档案）都存在**浏览器 localStorage** 里——刷新不丢，但**换设备、清缓存、换浏览器，全部归零**；而且每个人的数据互相看不见，永远只是单机玩具。
- **本周交付**：数据从浏览器搬进云端 PostgreSQL，公网 API 读写，刷新 / 换设备都能找回——「评分只在用户的浏览器里。不是我没做，是没后端。」这句话，本周正式作废。

## 第二段：核心流程——一次真实写入 + 刷新持久化（约 90 秒，现场操作）

按顺序在无痕窗口操作，每步说一句话：

| 步骤 | 操作 | 讲解词（要点） | 背后发生了什么 |
|---|---|---|---|
| 1 | 打开首页，点「开始抽卡」 | 页面上每张卡片都来自云端 | `GET /api/foods` 从 PostgreSQL 拉真实数据，不再是打包死的 mock |
| 2 | 进「食物库」，挑一道菜点❤收藏 | 注意，接下来这一下是本周的关键动作 | `POST /api/favorites/:foodId`，带上浏览器生成的匿名身份 `X-User-Id`，**真实写进云端数据库** |
| 3 | **F5 刷新页面**，回到那道菜 | 收藏还在——第 2 周这一下就没了 | App 启动时 `GET /api/favorites` 按 `X-User-Id` 把收藏拉回来，「刷新即丢」正式修复 |
| 4 | （备用加分项）F12 → Network，再点一次收藏 | 红框里就是真实的公网请求 | 让观众亲眼看到请求真的发往 `…tcloudbase.com/api` |

## 第三段：提示词改写——Day 17 的 PostgREST 转向（约 60 秒）

讲「本周最花时间的一步，以及提示词是怎么被现实逼着改写的」：

1. **原始提示词**（Day 15 计划）：技术设计文档里写的是用 `pg` 库在云函数里 TCP 直连 PostgreSQL——教科书式标准做法。
2. **现实打脸**（Day 17）：CloudBase 体验版是共享集群，**不提供 PG 连接地址**，`pg` 直连根本无处可连。代码一行没写，方案先死了。
3. **改写的关键**：不是把提示词润色得更漂亮，而是**把新约束喂进去**——「云函数连不上 PG 地址；官方文档提到 PostgREST REST API；改用 `fetch` + `Bearer API Key` 访问 `https://{envId}.api.tcloudbasegateway.com/v1/rdb/rest/{table}`，写操作加 `Prefer: return=representation`」。约束一变，方案跟着变，后面的代码反而顺了。
4. **教训一句话**：提示词改写改的不是措辞，是**前提**。前提错了，写得越工整错得越远。这一天卡得很疼，但换来 Day 18–20 三天纯增量。

## 第四段：验证方式（约 45 秒）

- **命令级**：curl 打公网地址，看状态码和返回体（上面预案里的四条就是，原始输出全部存档在 `docs/week3-acceptance.md` 证据 B/C）。
- **真人级**：同伴交叉验证——李国旭按固定步骤用自己浏览器操作，三行结论：**能打开 / 真实读写（收藏蛋炒饭刷新后还在）/ 无报错**（存档于验收表第三节）。
